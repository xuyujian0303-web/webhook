# 企业微信销售推送机器人后台版设计

## 目标

在现有 CSV 原型基础上，升级为一个可长期运行的正式版系统。该系统不再依赖本地 CSV 和本地图片文件，而是改为调用 IT 提供的销售数据接口和商品图片 URL，并增加一个供少量内部人员使用的网页后台，用于登录后维护筛选规则。

第一版正式目标：

- 定时查询销售接口
- 聚合销售整单
- 按后台配置规则筛选
- 将命中的销售单推送到企业微信 webhook
- 支持少量内部人员登录后台维护规则
- 规则保存后立即生效

## 适用范围

本设计覆盖以下范围：

- 管理后台登录
- 筛选规则管理
- 定时查询和推送执行
- 推送记录和运行状态展示
- 企业微信消息推送

本设计不包含：

- 复杂审批流
- 多租户设计
- 大规模权限体系
- 多消息渠道联动

## 推荐方案

采用单体 Web 后台方案。

即一个系统同时包含：

- Web 管理后台
- 定时任务执行器
- 规则引擎
- 推送逻辑
- 数据库存储

推荐理由：

- 部署简单
- 与当前原型演进路径一致
- 规则修改后可立即生效
- 适合少量内部人员使用
- 无论部署在公司服务器还是云服务器都容易落地

## 总体架构

系统包含 5 个核心部分：

### 1. Web 管理后台

用于内部人员登录后维护规则和查看结果。

后台至少包含：

- 登录页
- 规则列表页
- 规则编辑页
- 推送记录页
- 系统状态页

### 2. 定时任务模块

负责按固定周期执行查询和推送流程。

默认建议周期：

- 每 20 分钟执行一次

执行方式：

- 常驻服务内部调度
- 单轮执行结束后等待下一周期

### 3. 数据采集模块

负责调用 IT 提供的销售数据接口，获取最近一段时间的销售明细。

第一版建议由接口支持按时间范围查询：

- 起始时间
- 结束时间

如果接口不支持增量条件，则由系统拉取固定时间窗口数据并自行去重。

### 4. 规则引擎

负责读取当前已启用规则，并判断每张销售单是否命中。

支持两种规则组合模式：

- 任意满足
- 全部满足

### 5. 推送模块

负责将命中的销售单转换成企业微信 `markdown_v2` 消息，并调用 webhook 发送。

图片不再由本地服务提供，而是直接使用 IT 提供的可访问图片 URL。

## 数据流

每轮任务执行时按如下流程运行：

1. 读取系统当前生效规则
2. 调用 IT 销售接口，获取本轮需要判断的销售数据
3. 按销售单号聚合为整单
4. 根据规则模式执行匹配
5. 对命中销售单生成消息内容
6. 直接附带 IT 提供的图片 URL
7. 调用企业微信 webhook 发送
8. 成功后记录推送记录和销售单状态
9. 失败时记录错误，不标记成功
10. 更新本轮扫描时间

## 规则模型设计

后台中的规则建议采用“规则组 + 条件列表”的结构。

### 规则组

每个规则组包含：

- 规则名称
- 是否启用
- 匹配模式
- 条件列表
- 创建时间
- 更新时间
- 更新人

匹配模式枚举：

- 任意满足
- 全部满足

### 条件类型

第一版至少支持以下条件：

- 金额阈值
- 款号名单
- 门店名单
- 时间段
- 品牌
- 商品类别

条件设计要求：

- 同一规则组可包含多个条件
- 条件可增删
- 条件值支持录入多个选项
- 保存后立即生效

## 后台页面设计

### 登录页

字段：

- 用户名
- 密码

要求：

- 登录成功后进入规则列表页
- 未登录不可访问后台页面

### 规则列表页

用于查看当前所有规则。

字段建议：

- 规则名称
- 启用状态
- 匹配模式
- 更新时间
- 更新人

操作：

- 新建规则
- 编辑规则
- 启用/停用规则

### 规则编辑页

这是后台的核心页面。

应包含：

- 规则名称
- 启用状态开关
- 匹配模式选择
- 条件编辑区
- 保存按钮

条件编辑区至少支持：

- 金额阈值输入
- 款号名单输入
- 门店名单输入
- 时间段输入
- 品牌输入
- 商品类别输入

保存后规则立即写入数据库并生效。

### 推送记录页

用于查看系统已经推送过的销售单。

字段建议：

- 推送时间
- 销售单号
- 店铺
- 总金额
- 命中规则
- 推送状态
- 错误信息

### 系统状态页

用于查看任务是否正常。

建议展示：

- 最近一次扫描时间
- 最近一次扫描结果
- 最近一次推送成功数量
- 最近一次推送失败数量
- 最近错误日志摘要

## 权限设计

第一版权限建议采用最小可用方案。

角色建议：

- 管理员：可管理账号、编辑规则、查看记录、查看状态
- 运营人员：可编辑规则、查看记录、查看状态
- 只读人员：仅查看记录和状态

第一版如果要控制复杂度，也可先实现：

- 管理员
- 普通用户

## 状态与记录

系统至少要保存以下数据：

- 用户账号信息
- 规则组与规则条件
- 已推送销售单记录
- 每轮扫描时间
- 每轮执行结果
- 推送失败日志

状态记录的核心目的：

- 防止重复推送
- 支持问题排查
- 支持查看运行情况

## 企业微信消息

消息仍然使用企业微信 webhook 的 `markdown_v2` 类型。

图片处理改为：

- 直接使用 IT 提供的商品图片 URL
- 不再依赖本地图片目录
- 不再依赖本地 HTTP 图片服务

这能解决当前原型阶段遇到的“手机端无法访问本机图片地址”的问题。

## 部署建议

正式版可以部署在以下任一环境：

- 公司长期在线服务器
- 云服务器

推荐顺序：

1. 如果 IT 接口和图片 URL 主要是公司内网资源，优先部署在公司服务器
2. 如果 IT 接口和图片 URL 可在公网稳定访问，再考虑云服务器

无论部署在哪，都必须满足：

- 服务器 24 小时在线
- 能访问 IT 数据接口
- 能访问图片 URL
- 能访问企业微信 webhook
- 能运行 Web 服务和定时任务

## 运行方式

系统运行后是一个常驻服务。

包括两部分：

- Web 后台持续提供页面访问
- 定时任务持续按周期执行

规则修改后不需要重启服务，下一轮任务直接读取最新规则。

## 错误处理

### 销售接口失败

- 记录错误日志
- 不更新本轮成功扫描时间
- 不推进推送状态
- 等待下一轮重试

### webhook 推送失败

- 记录失败信息
- 不标记该单为已推送
- 后续可重试

### 图片 URL 缺失

- 仍发送文字消息
- 在消息中注明无图
- 不因为单个商品无图而阻断整单推送

### 规则配置错误

- 后台保存时做字段校验
- 阻止无效规则直接生效

## 测试要求

正式版至少应覆盖以下测试：

- 登录鉴权测试
- 规则保存后立即生效测试
- 规则模式“任意满足”测试
- 规则模式“全部满足”测试
- 定时任务单轮执行测试
- webhook 推送成功测试
- webhook 推送失败测试
- 防重复推送测试
- 图片 URL 直接透传测试

## 第一版实施边界

为控制复杂度，第一版正式版建议只实现：

- 账号密码登录
- 基础角色权限
- 规则管理页面
- 定时扫描
- 企业微信推送
- 推送记录和状态页

先不做：

- 审批流
- 多组织隔离
- 多渠道推送
- 高级报表

## 结论

正式版推荐采用单体 Web 后台方案。

该方案最适合当前业务阶段，能同时满足：

- 接入 IT 数据接口
- 使用 IT 图片 URL
- 支持后台登录维护规则
- 少量内部人员使用
- 规则保存后立即生效
- 长期稳定自动推送到企业微信

后续如果业务复杂度继续提升，再从该单体系统演进为后台与任务服务拆分的结构也比较自然。
